# Reproduction

Every command below was actually run in this repository's development
environment while writing this document — not copied from a template.

## Environment

- Python 3.11.15
- Node 22.22.2, npm 10.9.7
- No external services required — SQLite is a local file, no Postgres/Redis/
  vector DB to stand up.
- LLM: Google Gemini API (`GEMINI_API_KEY`). Originally built against
  Anthropic Claude, ported mid-build — see `docs/improvement-changelog.md`
  Iteration 7.

## 1. Clone and install

```bash
git clone <this-repo-url>
cd Micro-Hackathon

# Backend
cd backend
python3 -m venv .venv
./.venv/bin/pip install -r requirements.txt
cd ..

# Frontend
cd frontend
npm install
cd ..

# Root-level env file (copy and fill in GEMINI_API_KEY)
cp .env.example .env
```

`backend/requirements.txt` pins exact versions (fastapi==0.115.6,
pydantic==2.10.4, pandas==2.2.3, sqlmodel==0.0.22, httpx==0.28.1, and
others — no `anthropic` package; Gemini is called directly via `httpx`).
`frontend/package.json` pins next==16.3.3, react==19.2.8; other frontend
deps use `^` ranges as generated by `create-next-app`.

## 2. Run the backend test suite (no API key required)

```bash
cd backend
./.venv/bin/python -m pytest -q
```

**Verified output at time of writing:** `151 passed` in under 2 seconds. This
covers the dataset profiler, all 11 deterministic tools, every one of the 8
pipeline stages (via a fake client — see `backend/tests/unit/fakes.py`), the
Gemini wire-format translation layer directly (`test_gemini_translation.py`
— message/tool/tool_choice translation, response parsing, thought-signature
round-tripping, 429 retry-with-backoff), the FastAPI endpoints (via
`TestClient` against a real SQLite file), the CORS configuration, malformed-
dataset handling, and the evaluation scorer's deterministic and LLM-judged
halves. None of this requires `GEMINI_API_KEY`.

## 3. Regenerate the synthetic evaluation datasets (no API key required)

```bash
./.venv/bin/python scripts/generate_datasets.py
```

**Verified output:** rewrites `datasets/*/data.csv` and `datasets/*/case.json`
for all 10 cases, byte-identical to what's already committed (fixed seeds per
dataset). `git diff --stat datasets/` should show no changes if run again
immediately.

## 4. Run the backend + frontend together

```bash
# Terminal 1
cd backend
export GEMINI_API_KEY=...
DATABASE_URL="sqlite:///$(pwd)/data/insightforge.db" ./.venv/bin/uvicorn app.main:app --port 8000

# Terminal 2
cd frontend
echo "NEXT_PUBLIC_API_BASE_URL=http://localhost:8000" > .env.local
npm run dev
```

Visit `http://localhost:3000`. **Verified live** (Playwright-driven browser
session, see `docs/improvement-changelog.md` Iteration 5): the landing page,
dashboard (empty state, then real run listings once runs exist), and analyze
page's dataset upload all work end-to-end against the real backend — e.g.
uploading `datasets/01_sales_decline/data.csv` shows "216 rows × 5 columns",
computed by the real profiler, not a mock. The full analyze-to-report flow
(upload → question → Analyze → report) works with a real `GEMINI_API_KEY`
set; without one, clicking "Analyze" fails with a clear, real error message
in the UI's error state rather than hanging or crashing.

## 5. Run the baseline agent on one case

```bash
export GEMINI_API_KEY=...
cd backend
./.venv/bin/python ../baseline/run_baseline.py ../datasets/01_sales_decline/data.csv \
  "Why did revenue decline in Q2 2024, and what should we investigate next?"
```

**Verified live.** Example real output: 774 input / 969 output tokens,
22.6s latency, `stop_reason=end_turn`, `cost_usd=0.0` (Gemini pricing pages
are network-blocked in this environment — see `docs/limitations.md`; token
counts are real, the $ conversion is honestly reported as unknown rather
than guessed).

## 6. Run the full evaluation sweep

```bash
export GEMINI_API_KEY=...
./.venv/bin/python evaluation/run_evaluation.py
```

**Verified live.** Writes `evaluation/results/baseline_results.json`,
`agent_results.json`, and `comparison.json`, and prints the `comparison`
object to stdout. Actual measured runtime: baseline mean 3.4s/case (min
2.5s, max 4.4s, total 33.8s for 10 cases); agent mean 65.9s/case (min 10.1s,
max 112.8s, total 659.4s for 10 cases) — the agent's 8+ sequential calls per
run plus free-tier rate-limit backoff (a real 15-requests/minute cap was hit
during this run; see `docs/improvement-changelog.md` Iteration 8) account
for the ~19x gap. Result: agent 80.0/100 mean vs. baseline 54.5/100 mean,
full breakdown in `docs/evaluation.md`.

To run a subset while testing: `--cases 01_sales_decline,05_marketing_roi`.

Note on reproducing the *exact* numbers: LLM output is stochastic. Re-running
this command will very likely produce a qualitatively similar result (agent
ahead on most or all cases, baseline's failures concentrated in fabricated
placeholder values) but not necessarily identical per-case scores — see
`docs/limitations.md` for why this run is evidence, not a fixed constant.

## 7. Frontend build and lint (no API key required)

```bash
cd frontend
npm run build
npx eslint .
```

**Verified output:** build compiles successfully, all 5 routes generate
(`/`, `/_not-found`, `/analyze`, `/dashboard`, `/reports/[id]`), TypeScript
check passes with zero errors, ESLint reports zero issues.

## What "full reproduction" currently means

All 7 steps above have been run for real in this environment, including the
live evaluation sweep. What remains genuinely open (see
`docs/limitations.md`): multiple trials to quantify how much of the per-case
score spread is signal vs. model stochasticity, and a re-run against a more
capable Gemini tier than the free-tier-quota-constrained
`gemini-3.5-flash-lite` used here.
